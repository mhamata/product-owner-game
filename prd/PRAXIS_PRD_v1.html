1. Executive Summary

Vision

PRAXIS is the real-world flight simulator for product managers. A browser-based multiplayer simulation where aspiring and working PMs practice decisions under uncertainty — with consequence-driven events, behavioural customer models, and AI-led retrospectives — until product judgment becomes a reflex.

The problem

Product management is learned by doing, but most people can't access the "doing." Books teach theory, Reforge charges $2,000/year for content consumption, CSPO workshops give 2 days of physical exercises that vanish when the whiteboards are wiped. Nobody offers what pilots and surgeons take for granted: a simulator where you practice consequential decisions at speed, with instant feedback, as many times as it takes to internalise the skill.

The solution

PRAXIS turns Zuzi Šochová's Business Value Game and the full CSPO curriculum into a web-native game engine that:

  • Removes all friction — zero spreadsheets, zero math. Players drag cards, commit decisions, see consequences
  • Replaces random dice with consequence-driven events — skipped refinement three sprints ago causes scope surprises now
  • Models customers as behavioural state machines, not happiness integers
  • Generates AI-led retrospectives after every game with alternate-history replays
  • Supports multiplayer Scrum roles — PO + SM + Developer co-op with role-specific views
  • Ingests real backlogs — paste your Linear/Jira, simulate next sprint before running it

5. Core Game Mechanics

Game structure

A Scenario = 6–24 iterations (sprints) based on mode. Each iteration has 5 phases:

  1. Discovery — review backlog, customer signals, prior retro notes
  2. Planning — order iteration backlog, set Sprint Goal (text), commit investments
  3. Commitment — lock the plan (like rolling the dice, but without dice)
  4. Execution — events unfold; player has 1–2 response moments
  5. Review + Retro — see results, customer reactions, AI feedback

Modes

ModeIterationsFocusTime
Tutorial3Mechanics, ordering, release20 min
Quick6Classic CSPO-style game45 min
Quarter12Adds hiring, budget, OKRs2 hrs
Year24Scaling, PMF crisis, competition4 hrs (or async)
Interview3Single high-pressure scenario, scored30 min

What the player manipulates (zero-friction UI)

  • Drag to order — the iteration backlog is a list; player drags items into order
  • Drop the release card — insert the release card anywhere in the ordered list; everything above it releases if done
  • Click to commit — one button, locks the order, triggers execution
  • Respond to events — when an event fires, a modal offers 2–3 choices
  • Write a Sprint Goal — one sentence; graded by AI for clarity & outcome-orientation
  • Accept / decline customer asks — each incoming ask shows its effort cost; declining has relationship consequences
All math (velocity calculation, happiness deltas, interest accrual, release checks) is hidden. The player sees consequences as stories, not numbers.

Commitment cap & story cost (preserves the dice's "you can only do so much" lesson)

Removing the dice must not remove the lesson that velocity is a hard constraint. PRAXIS handles this with three mechanics:

Mechanic 1 — Every story carries an explicit effort cost

  • Effort (points) is visible as a badge on each card
  • Cards are visually scaled to their effort (5-pt card is physically larger than 2-pt card)
  • Some items carry "effort: 5?" — meaning true cost is only revealed during execution (teaches refinement risk)
  • Release card always costs a fixed amount (3 pt by default, reducible via tech investment)

Mechanic 2 — Capacity range indicator (not a single number)

As the player drags cards into the iteration backlog, a capacity bar fills with zones:

ZoneVisualMeaning
0 → lower bound (e.g. 12)🟢 GreenSafe — guaranteed to complete
Lower → expected (e.g. 15)🟡 YellowRealistic — completes in most sprints
Expected → upper (e.g. 18)🟠 OrangeStretch — only completes on a good sprint
Above upper bound🔴 Red + wiggleOver-committed — tail items almost certainly drop

Critical design decision: PRAXIS does not block the player from over-committing. The visual warning is clear but the decision is theirs. Over-commitment is a muscle you unlearn through pain, not prevention. The execution phase shows what actually happened, and any items below the cutoff line fall back to the product backlog with a "didn't make it" animation.

Mechanic 3 — Capacity range shifts based on state (replaces random dice)

The range itself moves deterministically based on team state and prior decisions. No random roll.

State conditionEffect on capacity range
Fresh team, refined backlogTightens: 14–16 pts (high predictability)
Engineer on vacation / sickShifts down: 10–14 pts
New hire ramping upWidens: 10–17 pts (more variance)
Invested in DoD + automated testsTightens over time (variance reduces)
Scope surprise event mid-sprintNarrows mid-execution: 12–14 pts
Team burnt out from context-switchingShifts down AND widens: 9–15 pts

Customer asks as costed commitments (the "cost per ask" lesson)

Every customer ask that lands in the inbox includes its effort cost upfront. The player chooses:

  • Add to backlog — locks the cost into future capacity planning
  • Decline politely — costs relationship points with that customer
  • Negotiate (v2) — smaller scope variant for less effort

This is the mechanic that teaches "saying yes to everything fills your backlog with items that consume velocity." The PO skill of ordering + refusing is built here, not in the planning board alone.

Execution resolution (what happens after commit)

  1. Player commits an ordered iteration backlog (may be over capacity)
  2. Events fire based on behaviour-weighted deck
  3. Actual capacity resolves deterministically from state (no random dice)
  4. Items execute top-to-bottom in the committed order
  5. Items completing within capacity go to Done
  6. Items below the cutoff line fall back to Product Backlog with visual feedback
  7. If the release card is below the cutoff, nothing releases this sprint (expensive but instructive)
Teaching goal preserved: players learn that velocity is a real constraint, that each story has a non-negotiable cost, and that over-committing produces worse outcomes than planning to the lower bound. This is exactly the dice's lesson — delivered through visible causality instead of random rolls.

Hidden state exposed through signals

Hidden stateWhat player sees
Customer happiness scoreMessage from customer: "Priya: 'I'm starting to wonder if you heard my last ask'"
Velocity modifierTeam vibe signal: "The team is in flow this sprint" or "Two devs are out sick"
Tech debt accumulationWarning banner: "Item X will take 50% longer — hidden complexity"
Stakeholder trustExec reaction: "The CFO nods thoughtfully" vs "The CFO leaves the review early"

Scoring (end-game)

Not a single dollar number. A multi-axis radar chart:

  • Value delivered — revenue + strategic wins
  • Customer loyalty — happiness retention, referrals
  • Team health — morale, sustainable pace, no burnout
  • Stakeholder trust — alignment across functions
  • Product integrity — tech debt managed, DoD respected
  • Personal growth — new techniques unlocked, mistakes avoided vs prior games

What causes engagement transitions (teachable causality)

Why some customers become more engaged later (teaching moment)

The game teaches this explicitly through scenario narratives:
  • Activation moment: a release finally solves a pain the customer didn't articulate but was feeling. Triggers engagement jump. The lesson: customers often can't name what they need; observation beats surveys.
  • Social proof: another customer of the same archetype becomes vocal; this one wakes up to try. Lesson: community signals matter.
  • Credibility accumulation: after 3 consecutive on-time commitments, a skeptic becomes active. Lesson: trust is earned in drops, lost in buckets.
  • Role change: the customer gets promoted; now they need different outcomes. Lesson: stakeholders are moving targets.
  • External event: regulation change makes your product suddenly essential. Lesson: context shifts value.

Feedback mechanisms in-game (what the player sees)

  • Inbox messages — customers send feedback, bug reports, feature requests; frequency varies by archetype
  • Quiet signals — dormant customers show small activity pulses (or don't)
  • Reviews — occasional public reviews that affect acquisition of new customers
  • Referrals — advocate-level customers bring in new ones at random
  • Churn warnings — only visible if the player looks at the right signal (teaches attentiveness)

7. Event Engine (Dice Replacement)

The original Business Value Game uses a d6 for velocity variance. PRAXIS replaces this with a weighted event deck where probabilities shift based on the player's prior choices. Every event is a teaching moment because it's caused.

Event categories & base weights

CategoryBase weightExample events
Team health15%Engineer sick · New hire ramping · Team in flow state · Burnout warning
Tech surprises20%Hidden debt on item X · API vendor outage · Flaky test eats 2 days · Perf regression
Dependencies15%Legal review delayed · Platform team migration · Design review bottleneck
Scope surprises15%Item X is 2x effort · Hidden acceptance criteria · Integration doesn't work
Stakeholder events15%Exec demands feature · Customer escalation · Sales lost deal · Analyst call
Positive events10%Pair programming breakthrough · Earlier investment pays off · Press mention
External shocks10%Competitor launch · Regulation change · Macro event · Security advisory

How PO behaviour shifts probabilities

Prior behaviourProbability shift
Skipped refinement 2+ timesScope surprises: +15% · Estimate accuracy: −30%
Invested in DoDTech surprises: −20% · Positive events: +5%
Invested in tests / automationBug events: −40% · Velocity variance: −25%

Didn't talk to users (no discovery activity)"Wrong feature shipped" event: +40%

Event response mechanics

When an event fires, a modal offers 2–3 choices. Each choice has a visible and hidden consequence. Examples:

Event: Exec demands a scope addition mid-sprint

Options:

  • Accept the scope — exec trust +2, team morale −2, tech debt +1, current Sprint Goal probability of completion −30%
  • Defer to backlog refinement — exec trust −1 (short term), team morale 0, Sprint Goal preserved
  • Trade: accept scope, drop equivalent existing item — exec trust +1, team morale 0, no tech debt, current sprint goal mutated

Deck composition by scenario

Each scenario has its own event deck (20–50 cards). The deck mixes universal PM events (the above) with domain-specific ones (e.g., "Regulator asks for audit trail" in a fintech scenario; "HIPAA alert" in a health scenario).

7B. Technology & Platform Economics

Every sprint runs on top of code, infrastructure, tooling, and team practices that either compound advantage (investments pay forward) or compound cost (debt accrues silently). PRAXIS models this as a first-class game mechanic because it's the hardest real-PM decision: invest in the platform now and ship fewer features this sprint — or postpone and pay growing interest.

Principle: The dice in the original BVG teaches velocity variance. The tech backlog teaches the compounding nature of platform investment. Both must be modelled explicitly for the game to be complete.

Six hidden state variables tracked per game

VariableStart stateHow it moves
Release cost3 pt per release↓ with CI/CD, deploy automation investment · ↑ silently with debt accumulation
Capacity baseline15 pt/sprint↑ with framework upgrades, team training · ↓ with burnout, debt
Capacity variance±3Tightens with test coverage, DoD discipline · Widens with new hires, skipped refinement
Tech debt score0–100 scaleRises from shortcuts, skipped investment · Falls from refactors
ReliabilityHighFalls with cut corners · Rises with monitoring, test coverage
Cycle timeBaselineShortens with automation · Lengthens with accumulated debt

Tech Backlog (separate from Product Backlog)

A dedicated section of the backlog where the player can invest effort in platform work. Benefits apply to future iterations, not the current sprint.

Tech item (example)EffortBenefit (starts next iteration, permanent)
CI/CD Pipeline5 ptRelease cost drops from 3 → 1 pt permanently
Automated test suite4 ptBug event probability −50%; variance tightens by 1
Observability platform3 pt"Hidden complexity" events eliminated
Refactor core module6 ptTech debt −30; future estimates 20% more accurate
Dev team training (bundle)3 × 1 pt+1 capacity baseline for rest of game (when all 3 done)
Framework upgrade (bundle)3 × 2 pt+2 capacity baseline for rest of game (when all 3 done)
Knowledge documentation2 ptEliminates "key person leaves" risk; new-hire ramp halved
Security hardening4 ptRemoves security events from the deck
Design system5 ptUX-related stories cost 30% less going forward
Data platform6 ptUnlocks analytics-based scenarios; +1 per-sprint bonus to discovery

Scenarios define their own tech backlog, scaled to their domain (a fintech scenario would include compliance tooling; a consumer scenario would include marketing infrastructure).

Debt accumulation — the cost of ignoring

Tech debt accrues silently from:

  • Shipping items with incomplete Definition of Done (+5 debt per item)
  • Declining tech investment when the team flags it (+3 debt per refusal)
  • Every 3 iterations with zero tech investment (+10 debt automatic)
  • Responding to an event with the "shortcut" option (+2 to +8 debt depending on severity)

Debt thresholds — compounding consequences

Debt levelConsequence
≥ 30Release card silently grows from 3 → 4 pt
≥ 40Capacity variance widens by +1 (more unpredictable sprints)
≥ 50Customer-facing incident events enter the deck
≥ 60Release cost: 4 → 5 pt
≥ 70Capacity baseline drops by 2 (fewer points per sprint)
≥ 80Release cost: 5 → 6 pt; team morale events trigger; engineers quit
≥ 90"Critical outage" events force-fire; may end the game early in some scenarios

Thresholds are permanent until reversed — reducing debt back below 30 doesn't automatically shrink release cost. Players must explicitly invest in the right kind of refactor to reverse the damage. This models reality: once a platform decays, undoing the rot takes more effort than preventing it.

Making it teachable — narrative over numbers

Following the zero-friction principle, tech state is never shown as a raw number. It's exposed through in-game narrative signals:

Hidden stateWhat player sees
Debt rising past 30"The test suite is flaking. A dev mentions the backend is getting hard to change."
Release cost climbing"Last deploy took 2 days. The team spent more time debugging than shipping."
Capacity variance widening"The sprints feel inconsistent. Some weeks the team crushes it; other weeks nothing ships."
Capacity baseline dropping"Sprints feel slower. Nobody can put their finger on why."
Post-investment payoff"CI/CD is live. Deploys are one-click. Team visibly happier. Velocity is trending up."
Refactor payoff"The core module refactor is in. Estimates feel more accurate; scope surprises have dropped."
Silent decay"A senior engineer submits notice. They cited 'tech debt' as the reason."

Tech investment payoff moments (emotional design)

Each tech investment triggers a visible payoff moment the iteration after it lands — same celebration as a customer release. This is a deliberate design choice: real orgs under-celebrate platform wins; PRAXIS over-corrects so players feel why infrastructure matters.

The core PM teaching moment this creates

Every scenario forces the decision: invest now (sacrificing customer work this sprint) or postpone (paying growing interest later). The end-game retrospective explicitly grades tech decisions:

"You declined 3 tech investments in favour of features. Release cost rose from 3 to 5 pt. Your final sprint cost you 2 releases you would otherwise have made. A senior PM would have paid down CI/CD in iteration 2, worth +$4,200 in compounded value."

Integration with the event engine (Section 7)

Tech state directly feeds the event deck weights from Section 7. For example:

  • Low reliability → higher "outage" event weight
  • High debt → higher "scope surprise" event weight
  • High test coverage → lower "bug" event weight
  • Wide capacity variance → more variable iteration outcomes

This means tech decisions and customer decisions are not independent systems — they both feed the same event probability model. Neglect either side and events pile up. Balance both and events stay manageable.

8B. PM Behavior Patterns & Interaction Nudge System

PRAXIS teaches product management through scenarios, but scenarios alone are not enough. The deepest value comes from recognizing behavioral patterns that play out across many scenarios — the same mistakes in different costumes. A player may win a scenario but lose the career-long game if they don't see the pattern. This section defines the pattern-recognition system that turns PRAXIS from a knowledge-delivery tool into a behavior-change tool.

Design principle: Most PM training teaches frameworks. PRAXIS teaches reflexes. Reflexes are built by catching yourself in the moment, repeatedly, until the right move becomes automatic. The nudge system is how we produce that catch.

PM ↔ Developer interaction patterns (reference model)

Each pattern below has a "healthy" and an "anti" behavior. The game observes the player's choices and tracks both.

Real-time nudge system (in-game coaching)

When a player is about to take an action that matches a known anti-pattern, PRAXIS surfaces a subtle nudge — not a blocker. The player still makes the choice, but now with awareness.

Nudge delivery rules

  • Never block. The player can always proceed with the anti-pattern choice. Consequences teach; popups preach.
  • Never interrupt mid-drag. Nudges appear on commit, not during planning.
  • Time-box to once per pattern per game. If a player sees the "specifies_how" nudge once, they don't see it again that game — prevents nagging.
  • Tone: curious, not corrective. "Notice this pattern?" not "This is wrong."
  • Opt-out available. "Expert mode" disables in-game nudges; all tracking still happens for the retrospective.

Cross-game pattern recognition (the moat)

Single games teach scenarios. Cross-game pattern detection teaches you as a PM.

Player profile (private, visible to the player only)

After 5+ games, the player sees their own pattern dashboard:

  • Strengths — patterns they consistently do well (e.g., "Strong at customer coverage — 9/10 iterations with active customer engagement")
  • Edges — patterns they consistently struggle with (e.g., "Tends to accept scope mid-sprint — 11 instances across 8 games")
  • Trends — patterns improving or declining over time (e.g., "Tech debt decisions improving — declined 3 investments in early games, 0 in last 3")
  • Unlocks — mastery badges earned for 10+ consistent healthy patterns

AI retrospective integration (links to Section 9)

The end-of-game retrospective uses the pattern tracker as input. Instead of generic feedback, the AI mentor surfaces specific pattern evidence:

"Across this game and your previous 4, you've overruled your tech lead 3 times — twice publicly. Each time, the decision worked out in the short term, but team trust eroded. A senior PM would have taken the first disagreement offline and established the pattern that technical decisions live with engineering. Here's what that would have looked like in this game's Iteration 3…"

Cohort-level insights (trainer feature, Phase 2)

CSTs and L&D leads get a cohort dashboard showing aggregate patterns across their trainees (anonymised in aggregate, attributable only to the trainer). Answers questions like:

  • What's the most common anti-pattern in this cohort?
  • Which trainees are showing rapid behavior change?
  • Which scenarios triggered the most learning moments?

This turns PRAXIS from individual training into measurable organizational learning — key for enterprise sales.

Integration with the core engine

  • Pattern classification runs server-side on decision events
  • Claude Haiku 4.5 classifies text inputs (Sprint Goals, event responses) for implicit patterns
  • Rules-based classification for structural patterns (mid-sprint changes, inbox ignores)
  • Patterns stored in PostgreSQL linked to Game + User; aggregated in UserProgress
  • Cost per game: ~$0.04 (Haiku classification) + ~$0.12 (Opus retro) = ~$0.16 all-in
Strategic implication: the pattern library is proprietary content that compounds. Each player's games train the system on what "good" and "anti" look like across thousands of decision points. Competitors starting later can't easily replicate the behavioral training data.

Post-game retrospective — structure

AI-generated retrospective template (per game)
  1. Headline — one sentence that captures this game's defining decision
  2. 3 strengths — with specific moments timestamped
  3. 3 growth edges — with specific alternative decisions
  4. Alternate history replay — "Here's what would have happened if, in iteration 3, you had..."
  5. Technique unlocked — one framework the player demonstrated readiness for (Kano, WSJF, ICE, Cost of Delay, etc.)
  6. Recommended next scenario — based on growth edges

Prompt scaffolding (Opus 4.7)

The retrospective prompt includes: full game log (decisions, events, outcomes), scenario metadata, player's prior games (if any), PM principles library (Cagan, Torres, Patton, Šochová). Output validated against JSON schema for consistent UI rendering.

Prompt caching strategy

Scenario definitions + PM principles library + retrospective rubric are static per game — cache them with 5-minute TTL. Expected cache hit rate: 70%+, reducing average retrospective cost from $0.30 to ~$0.12.

Content safety

  • Retrospective tone is constructive, not shaming. Prompt explicitly forbids ridicule.
  • No personal data in prompts (use game state IDs, not real names).
  • All AI output labelled; players know what's AI-generated.

Systems diagram (narrative)

Player's browser runs Next.js app. Game engine state lives in Postgres (persistent) + Redis (hot state during play). Decisions mutate state via tRPC. Event engine runs server-side, consults Claude Haiku for dynamic narration, writes results back. Post-game, Claude Opus generates retrospective (background job). PostHog ingests every decision event for analytics.

Game engine design (critical)

  • Pure deterministic core — given state + action, always produces same result. Enables replay, debugging, and scenario testing.
  • Event log — every decision and outcome stored as append-only log. Enables replay and alternate-history simulation.
  • Deterministic randomness — seed-based PRNG per game; same seed + decisions = same game. Enables "replay with different strategy."
  • Engine is a library, not a service — can run in browser for tutorial, on server for real games.

14. UI / UX Design Principles

Five zero-friction principles

  1. No numbers on screen unless essential. Use progress bars, sentiment icons, message tone — not integers.
  2. One primary action per screen. Planning = drag + commit. Review = read + continue. Retro = absorb + next.
  3. Animations carry meaning. A customer becoming an advocate gets a real celebration moment. A churn gets a quiet dimming, not a red banner.
  4. Progressive disclosure. Hide advanced mechanics (tech debt meter, stakeholder trust) until the player's behaviour unlocks them.
  5. No manual saves. Every decision auto-persists. Game is always resumable from any device.

Key screens (MVP)

  1. Onboarding — 3 screens: welcome, tutorial start, first drag
  2. Home/Library — scenarios + progress + recent retros
  3. Planning board — the drag-drop canvas (most used screen)
  4. Customer inbox — message list + customer detail panel
  5. Event modal — event narrative + choices
  6. Sprint Review — animated recap
  7. End-game retrospective — AI-generated report
  8. Account/Billing — settings + Stripe portal

Design system

shadcn/ui as base. Custom components for card drag, release moment animation, customer avatar grid. Typography: Inter. Colour palette: warm neutrals + deep teal accent + single "victory" gold for releases.

Accessibility (non-negotiable for MVP)

  • Full keyboard navigation for drag-drop (dnd-kit built-in)
  • Screen reader-friendly state changes
  • WCAG AA contrast throughout
  • Reduced-motion mode for animations

16. Security, Privacy & Compliance

Auth & access control

  • Clerk for auth (email + Google + LinkedIn). MFA optional free; required for enterprise tier.
  • Row-level security via Prisma middleware — users only see their own games.
  • Trainer/cohort roles: CSTs can view games of users in their cohort.

Data handling

  • PII (email, name) stored in Postgres with encryption at rest (Supabase default).
  • Game data (no PII beyond user_id) retained indefinitely unless user requests deletion.
  • AI prompts never include PII — only game state IDs and generated narrative.
  • Stripe handles all payment data (PCI offloaded).

Privacy compliance

  • GDPR: right to export (Game + Retrospective JSON), right to delete (hard delete with cascade).
  • CCPA: Do Not Sell toggle in account settings.
  • Canadian PIPEDA: relevant for Mike's home jurisdiction; handled by above controls.
  • Cookie banner with analytics opt-out.

AI safety

  • Retrospective prompts include explicit system message: "Feedback must be constructive, specific, never shaming."
  • User-facing AI outputs labelled "Generated by Claude".
  • Anthropic's Prompt Shield + usage policies enforced.
